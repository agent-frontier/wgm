### The recurring citation-hyperlinking gap (headline finding)
This is the most important finding this round precisely because it is a **process-reliability
signal**, not a one-off content nit — the PM's headline finding (consolidated above as **Fix 9**) is
its third appearance:

1. **Round 2** (PR #46): bare `saitarrun/devforge-ai` mentions fixed, no durable rule written.
2. **Round 3** (PR #49): bare `foundatron/octopusgarden`/`Aider-AI/aider`/`RooCodeInc/Roo-Code`
   mentions fixed **and** a durable rule added to `references/self-improvement.md`: "Hyperlink the
   citation's fullest or first mention... not just a bare backticked name."
3. **Round 4** (this batch, merged roughly one hour after PR #49): the identical defect shape
   recurred — `ralph-claude-code` and `codeburn` landed as bare/unlinked citations in brand-new
   content, despite the written rule already being in force.

The three concrete instances this round are fixed (Fix 9, above). The open question is whether to
add a low-false-positive automated check to `scripts/check-docs.sh` so a 4th recurrence is caught
mechanically instead of by a fifth manual audit pass. **Decision: deferred, not implemented**, for a
specific, tested reason rather than by default:

- Prototyped the exact suggested heuristic — an `` `owner/repo` ``-shaped bare-backtick regex across
  `references/*.md` with no adjacent markdown link — and iteratively refined it (excluding known
  path-roots, file-extension endings, and anything linked anywhere else in the corpus).
- Even the refined version produced false positives on real, non-citation text already in the repo:
  `./.copilot`, `.agents/skills`, `PATH/wgm`, `owner/name`, `wgm/swarm`, `origin/main`,
  `feat/dx-update-and-release-install`, `API/UX`, `Utilities/idioms` — git refs, branch names,
  install paths, placeholder text, and ordinary prose word-pairs, none of which are citations.
- More importantly, the `` `owner/repo` `` shape **cannot catch this round's actual two
  violations** — `ralph-claude-code` and `codeburn` are both bare *single words* with no slash,
  structurally outside what that check type can ever match. A check narrow enough to avoid false
  positives would not have caught this round's real defects; a check broad enough to catch bare
  single-word tool names would require a hand-maintained allowlist of every external tool name wgm
  has ever cited (itself a new drift-prone registry) or would flag hundreds of legitimate code
  identifiers, CLI flags, and config keys repo-wide.
- Implementing only the "safe" narrow form would have given false confidence without solving the
  actual recurring problem, which is worse than being explicit that it's still open.

This is therefore reported honestly as an **unresolved, recurring process-reliability risk** — not
silently fixed-and-forgotten a third time — and is the reason this round's overall verdict is AMBER
rather than GREEN. It is worth a dedicated future pass (design a check that can reliably catch
bare single-word tool-name citations without a maintained allowlist, or accept that this stays a
manual-review item and add a docs-audit checklist line making the check explicit every round) rather
than a fourth ad-hoc manual fix that is likely to face the same fate.
